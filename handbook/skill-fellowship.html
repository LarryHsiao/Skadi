The Fellowship of Skills

One map of all fifty-three skills — where each stands on the arc of the work, and which of them call which.

Two things are drawn here at once, and they are kept apart on purpose. Position carries the workflow: a skill’s lane is the stage of the work it serves, read left to right, Intake through Watch. Arrows carry one thing only — a real dispatch, one skill invoking another. Nothing is drawn between lanes merely because one stage follows another; the lanes already say that. So an arrow you see is a call that genuinely happens.

Chapter I walks the Work Loop’s eight stages and names no skills; Chapter II draws the ticket arc and names a handful. This chapter is neither — it is the whole roster, and the arrows that bind it. Where you want the reasoning behind a stage rather than its cast, follow the link back to I or II.

Rendered in the browser by mermaid, fetched from a CDN — offline it falls back to its plain source, which still reads. That source is authored with both languages in each lane title; the toggle above picks one and redraws, so only one language is ever on screen.

The one true cycle

Every other arrow on the map runs forward, or sideways into a dashboard. One runs backwards, and it is drawn in red because of it. A change that has been forged, weighed and opened as a PR can still draw comments — and /moria sweeps every repo for them, /durin narrows that to one repo, /narvi answers a single comment with code. That code re-enters the Forge lane, and /narvi weighs its own amendments by Mithrandir’s axes before it pushes — so the ring closes back on /mithrandir, where it began.

This is why a standing /mithrandir Blocker halts a Narvi run rather than pushing past it: a loop that mends its own mends has nothing to stop it. The red ring is the only place in the whole system where a skill can hand work back to an earlier stage with no human in between, and it is fenced accordingly.

The Work Loop, and which skills serve it

Chapter I’s eight stages are mostly rules, not skills — the gauge, the acceptance lines, the approval are things you write, not things you call. Only five of the eight have a skill standing in them at all. Naming that plainly is more useful than drawing an eight-spoked ring half of which would be empty.

Work Loop stage Skills that serve it
1. Task Sizing none — the gauge is written, not called
2. Acceptance none — outcomes named in the gate block
3. Change Approval none — the human’s word
4. Previews /henneth serves them, /galadriel mirrors a plan, /rumil writes the plan being mirrored
5. Implementation Loop /narya keeps the app alive, /feanor mends against a spec, /manwe weighs a single render
6. Compliance Review a spawned read-only agent — /nazgul where a rubric fits the check
7. Verification /argonath gathers the toolchain, /nazgul audits the tree
8. Done /commit, /celebrant to merge, /handoff for the worklog entry

The full reasoning for each stage is Chapter I — The Skadi Work Loop. The ticket-bound version of the same arc is Chapter II — Plan · Forge · Review.

Three that stand alone

/findegil, /focus and /scribe dispatch to no skill, and no skill dispatches to them — drawn with a dashed border. They are not orphans in need of wiring; each answers a need the arc does not touch. Findegil rewrites notes into prose, Focus keeps a Pomodoro clock, Scribe files a document. A skill earns an arrow by needing another skill’s work, and these three do not. Erestor’s notes name /scribe once, as one way an issue might be carved — but naming is not calling, which is the whole point of the two arrow kinds above.

唯一真正的迴路

圖上其他每一支箭頭要嘛往前走，要嘛橫向流進某個儀表板。只有一條是往回走 的，所以它畫成紅色。一個已經鍛造、衡量、開成 PR 的變更，仍然可能收到留 言——/moria 掃過所有 repo 找這些留言， /durin 把範圍收斂到單一 repo， /narvi 則用程式碼回應單一則留言。那份程式碼重 新進入 Forge 欄位，而 /narvi 在 push 之前會先 用 Mithrandir 的準則衡量自己的修補——於是這個環回到 /mithrandir，也就是它出發的地方。

這也是為什麼一個尚未解除的 /mithrandir Blocker 會讓 Narvi 停下、而不是硬推過去：一個會修補自己修補的迴路，沒有 東西攔得住它。這條紅環是整個系統裡唯一一處，skill 可以在沒有人介入的情 況下把工作交還給更早的階段，因此圍籬也下得特別重。

Work Loop，以及服務它的 skill

Chapter I 的八個階段大多是規則而非 skill——量尺、驗收條件、核可都 是你寫下來的東西，不是你呼叫的東西。八個階段裡只有五個真的有 skill 站在 裡面。把這件事講清楚，比畫一個八根輻條、其中一半是空的環要有用。

Work Loop 階段 服務它的 skill
1. Task Sizing 無——量尺是寫出來的，不是呼叫出來的
2. Acceptance 無——在 gate 區塊裡點名的可觀察結果
3. Change Approval 無——由人開口
4. Previews /henneth 負責供稿， /galadriel 映出計畫， /rumil 寫出被映出的那份計畫
5. Implementation Loop /narya 讓 app 保持存活， /feanor 對著 spec 修補， /manwe 衡量單一畫面
6. Compliance Review 另外派出的唯讀 agent——若某條 rubric 對得上，則用 /nazgul
7. Verification /argonath 匯集整套工具鏈， /nazgul 稽核整棵樹
8. Done /commit、合併用 /celebrant、worklog 用 /handoff

每個階段完整的道理見 Chapter I——The Skadi Work Loop。同一條路綁上 tracker 的版本見 Chapter II——Plan · Forge · Review。

三個獨行者

/findegil、 /focus 與 /scribe 既不 dispatch 任何 skill，也不被任何 skill dispatch——因此邊框畫成虛線。 它們不是等著被接線的孤兒；每一個回應的都是這條路徑碰不到的需求。Findegil 把筆記改寫成文章，Focus 顧著番茄鐘，Scribe 歸檔文件。一個 skill 是因為需 要另一個 skill 的成果才長出箭頭，而這三個不需要。Erestor 的筆記裡確實提 過一次 /scribe，說那是開票的其中一種途徑——但 「提到」不等於「呼叫」，這正是上面兩種箭頭要分開的理由。

The same web, without the lanes

The map above imposes an order the skills themselves do not have. Here the same fifty-three are turned loose: no stage, no left-to-right, only pull and repulsion. Skills that call each other draw together; skills that call nothing drift to the edge. Scroll to zoom, drag the canvas to pan, drag a node to pull it free — release it and the web settles again.

Nothing here is new data. The network is read from the very same mermaid source printed above — one edge list, two drawings, so they cannot drift apart. Colour carries a coarse band rather than the eight lanes, because eight hues cannot be told apart reliably when any two may land side by side; the lane itself is on every node’s tooltip, and the buttons single one out.

同一張網，拿掉欄位

上面那張圖強加了一種 skill 本身並不具備的順序。這裡把同樣的五十三個放 開：沒有階段、沒有左到右，只有牽引與排斥。互相呼叫的會靠攏，誰都不呼叫 的則漂到邊緣。滾輪縮放、拖曳畫布平移、拖曳節點把它拉開——放手之 後，網會自己重新安定下來。

這裡沒有任何新資料。這張網是直接讀上面那份 mermaid 原始碼建出來的——一 份邊清單、兩種畫法，所以它們不可能各說各話。顏色承載的是較粗的分帶而非 八個欄位，因為當任兩種顏色都可能並排出現時，八種色調無法可靠地分辨；欄 位本身寫在每個節點的提示上，按鈕則可以單獨標出其中一欄。
