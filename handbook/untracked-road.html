The Untracked Road

One diagram, top to bottom — PRD and mockups to a merged change — drawn without an issue tracker in the loop.

Chapter II tells the same road with a ticket at its centre — every gate a comment on a Jira or YouTrack thread. This chapter strips that out: no tracker, no ticket, no bracketed gate token. Where Chapter II names /council, /glorfindel, /working, /celebrimbor, /aule and the sweep layer (/anduin, /rhovanion, /amon-sul) as the engine driving Plan and Forge — all of them ticket-bound — this chapter strips every one out. Forge is left with no skill to put in their place: a human opens the branch and drives the implementation by hand. Plan is not quite empty, though — /rumil reads a spec and its mockups directly and writes the plan itself, needing no ticket and no tracker to run, so it keeps its place here where the tracker-bound /council could not. Reach for this road when there is no tracker to summon, or when the shape of the whole arc matters more than which skill drives which step.

Reading it

  • Input & Plan — /rumil takes the PRD and the Figma mockups together, wires the text's rules to the mockups' screens, raises what falls out as questions rather than settling them quietly, and writes the plan itself; /galadriel renders that plan file into a progress mirror. See Chapter IV, “The Rúmil Road”, for this step's own long form.
  • The Free-Form Gate — before Forge begins, the human is shown the work's size, its Acceptance lines (the observable outcomes a test or an eye can check), and its Non-goals, and confirms before anything is touched. This is where Acceptance Criteria live — not inside the plan document, but in this one gate the human renders judgment on. Every step's verification in the Loop below, and Compliance Review's spec-compliance pass, both check their work against the lines drawn here.
  • Forge — a branch opens, implementation follows the plan; /narya hot-reloads continuously through it; the PR/MR opens only once the Implementation Loop below has run its course.
  • The Implementation Loop — the rhythm inside “implement per the plan”: one step at a time, each layered on what already runs rather than sliced horizontally. This is where the unit test is written — new code lands with its test in the same step, never as a follow-up. Each step's verification checks both the test and, where the step closes one, an Acceptance line from the Gate; a step that fails either, or a scope that has grown past its gauge, stops the loop rather than pushing through. Once every step closes, Compliance Review weighs spec compliance — reading the Gate's Acceptance lines as what was promised — then code quality, and a fresh verification — this turn's own run of the static analysis and test suite — closes the loop before the PR opens.
  • Pre-commit gate — /nazgul walks its nine checks; /argonath weighs the diff and the merge risk together; /commit composes the message and commits.
  • Review & Mend — /mithrandir renders the multi-axis verdict; /mandos checks the direction is right; /narvi answers each comment with its own commit; /durin and /moria carry that sweep across a repo and across repos.
  • Merge — /celebrant completes a --no-ff merge, pushes, and prunes the branch.
  • Daily / upkeep — /preflight, /eod, and /cleanup-dev keep the environment sound, running alongside the feature road rather than on it.

See Chapter I for the Implementation Loop's own long form — Task Sizing, Acceptance, Approval, Compliance, Verification — and Chapter II for the same arc with a tracker at its centre.
