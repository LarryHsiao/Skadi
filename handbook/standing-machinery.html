The Standing Machinery

Four pieces that outlive a single turn — a server kept answering, a daemon fed one line at a time, a runner a session hands work to instead of spawning its own, and the registry naming which config root belongs to which profile.

Chapter VI maps every skill by the stage of work it serves. None of what follows is a skill in that sense — it is the standing state those skills, and the sessions calling them, read and write between turns. It grew alongside the fellowship without ever joining the map.

常駐機制

四樣活得比一個 turn 還久的東西——持續應答的伺服器、一次餵一行的 daemon、session 拿去外包工作而非自己生 subagent 的 runner，以及 記錄哪個 config root 屬於哪個 profile 的登記表。

Chapter VI 按工作階段把每個 skill 都畫進圖裡。以下這些都不是那個 意義上的 skill——它們是那些 skill、以及呼叫它們的 session，在 turn 與 turn 之間讀寫的常駐狀態。它們跟著整個 fellowship 一起 長出來，卻從未被畫進那張圖。

I. The windows row

Any script starting a local server a person might want to click into — a Flutter DevTools session, a blog preview, anything else — drops a two-line file under ~/.skadi/windows via hooks/window-register.sh: url on line 1, label on line 2. statusline.sh draws each as an OSC 8 terminal hyperlink, so the port costs no width on the line and a click opens the window.

Liveness is a /dev/tcp connect rather than a curl probe, because the statusline redraws constantly and a heavier check would be paid on every redraw. A file whose server has gone silent is pruned on sight — the registering script may have died without calling unregister, and a label that opens nothing is worse than no label — so calling unregister on a clean shutdown is a courtesy, not a requirement.

Registered servers get their own row at the very top of the statusline, above the built-in Standing Windows row that already names the board, Henneth, the plan mirror, and the skills cheatsheet: a server the user chose to register just now is the thing they most likely want to click, so it leads rather than waits its turn.

II. Vilya and Narya — daemons that outlive a turn

Both hold one long-lived process per named slot. The expensive setup — a Flutter build, a dev server's cold start — is paid once; every later turn or session pokes the standing process for pennies. Neither boots a device or a browser, and neither navigates — holding the process and reading its state is the whole of the job.

/narya keeps a flutter run --machine session alive behind a named pipe, so a source edit reaches the running app in about a second instead of a 60–90s rebuild, without losing the screen you navigated to. /vilya holds a protocol-less server — a Vite or webpack dev server, a Zola or Hugo preview, an API mock — one per (project, name), and its ready verb reads the server's own log for a pattern rather than sleeping and hoping, so a caller acts on a signal instead of a guess. Both register themselves on the windows row above; any caller may poke either — you in chat, /feanor between mends, /manwe before a shot.

One gap stands open honestly: Vilya's plan replaced /feanor's fixed settle-and-reshoot with a real ready gate, and that prose has shipped — but one real /feanor pass against a Vilya-held server, the thing the plan's own verify line asks for, has not yet run. See TODO.md at the repo root.

III. The external runner

~/.skadi/profiles/<profile>/subagent-runner.md names a CLI a session hands delegated work to instead of spawning an Agent-tool subagent, for the profile named by SKADI_PROFILE — which the installer stamps into each root's settings.json. Its first line is the runner's non-interactive command template (prompt on stdin, {model} standing in for the slug); the lines after map the delegation roster's mechanical= / default= / strong= tiers onto that runner's own models. So a work profile may dispatch through Codex while the personal profile keeps to the Agent tool.

The file's absence means the question was never asked; the literal value none means it was asked and declined. install.sh never writes this file itself — it only prints a hint for a profile left unset — because which runner a profile uses, and whether spare quota stands behind it, is a choice about that profile and that machine, not a fact the config can know on its own.

IV. Profiles and roots.tsv

~/.skadi/install/roots.tsv holds one tab-separated row per profile / claude-root / codex-root. install.sh --all installs every registered row; --pair registers one more.

A fresh machine is registered with one pair, not three, and the reasoning is worth drawing out: two of the three homes would stand empty, and the mere existence of a ~/.claude-* sibling flips ~/.claude/CLAUDE.md to the stub on the next run — quietly demoting a live root to a signpost. A second profile is a choice made with --pair, never a default taken on the user's behalf. Launching a profile once paired is CLAUDE_CONFIG_DIR / CODEX_HOME, which the install hint names directly.

I. 視窗列

任何啟動本機伺服器、而使用者可能想點進去看的腳本——Flutter DevTools session、部落格預覽、或其他——都會透過 hooks/window-register.sh 在 ~/.skadi/windows 底下丟一個兩行檔：第一行是 url， 第二行是 label。statusline.sh 把每一筆都畫成 OSC 8 終端機超連結，所以連 port 都不佔狀態列的寬度，點一下就能開啟 那個視窗。

存活判斷用的是 /dev/tcp 連線，而不是 curl 探測—— 因為狀態列不斷重繪，較重的探測每次重繪都要付一次代價。伺服器 已經無聲的檔案會被見即清除——註冊用的腳本可能沒呼叫 unregister 就死掉了，而一個打不開任何東西的 label 比沒有 label 還糟——所以乾淨關閉時呼叫 unregister 只是禮貌，不是必要。

已註冊的伺服器會出現在狀態列最上方自己的一列，排在原本就存在 的 Standing Windows 列（board、Henneth、plan mirror、skills cheatsheet）之前：使用者剛剛選擇註冊的伺服器，最有可能是他們 現在就想點的那個，所以它排在最前面，不必等輪到它。

II. Vilya 與 Narya——活得比一個 turn 久的 daemon

兩者都是每個具名的 slot 守住一個長駐 process。昂貴的初始化—— 一次 Flutter build、一次 dev server 的冷啟動——只付一次；之後 每個 turn 或 session 戳一下常駐 process 都只是零錢的代價。兩者 都不開裝置、不開瀏覽器，也不做任何導覽——守住這個 process、 讀它的狀態，就是全部的工作。

/narya 在具名 pipe 後面守住一個 flutter run --machine session，讓原始碼的修改在 約一秒內就送進正在跑的 app，而不是 60–90 秒的重建，也不會 丟失你原本導覽到的畫面。/vilya 守住 一個無協議的伺服器——Vite 或 webpack 的 dev server、Zola 或 Hugo 的預覽、API mock——每個 (project, name) 一份，它的 ready 動詞直接讀伺服器自己的 log 找特定樣式，而不是睡一下賭運氣，讓呼叫端能等一個訊號、而不是 用猜的。兩者都會自己註冊到上面的視窗列；任何呼叫端都能戳 其中一個——你在聊天視窗裡、/feanor 在兩次修補之間、/manwe 在拍照之前。

有一個缺口老實地留著：Vilya 的計畫把 /feanor 原本「等幾秒再重拍」的做法 換成真正的 ready 關卡，這段文字已經上線——但計畫 自己驗證那行要求的、對著 Vilya 守住的伺服器跑一次真正的 /feanor，還沒有真的跑過。見倉庫根目錄 的 TODO.md。

III. 外部 runner

~/.skadi/profiles/<profile>/subagent-runner.md 記錄一個 session 拿去外包工作、而不是自己生一個 Agent-tool subagent 的 CLI，profile 取自 SKADI_PROFILE—— 由 installer 寫進每個 root 自己的 settings.json。 第一行是這個 runner 的非互動指令樣板（prompt 走 stdin， {model} 代表 model slug）；之後幾行把 delegation roster 的 mechanical=／default=／ strong= 三個分級對應到那個 runner 自己的 model。 所以 work profile 可以走 Codex 外包，personal profile 則仍然 用 Agent tool。

這個檔案不存在，代表從沒被問過；內容寫死是 none， 代表問過但被拒絕了。install.sh 本身從不寫這個 檔案——只會替還沒設定的 profile 印出提示——因為某個 profile 該用哪個 runner、背後是否還有餘裕的額度，是關於那個 profile 與那台機器的選擇，不是設定檔自己能知道的事實。

IV. Profile 與 roots.tsv

~/.skadi/install/roots.tsv 每一列都是一組 tab 分隔的 profile / claude-root / codex-root。install.sh --all 會安裝 登記表裡的每一列；--pair 再多登記一組。

一台全新的機器只會登記一組，不是三組，這個理由值得 寫清楚：三個 home 裡有兩個會是空的，而且光是 ~/.claude-* 這種 sibling 存在，就會讓 ~/.claude/CLAUDE.md 在下一次執行時翻成 stub—— 悄悄把一個活著的 root 降級成路標。第二個 profile 是用 --pair 主動做出的選擇，絕不是替使用者預設好的。 配好之後要啟動某個 profile，就是 CLAUDE_CONFIG_DIR / CODEX_HOME， install 的提示文字會直接點名。
