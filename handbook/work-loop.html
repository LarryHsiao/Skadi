The Skadi Work Loop

From the weighing of a task to the word “done” — the free-form cycle, with Acceptance now named up front.

1. Task Sizing

Weigh the craftsman’s triad and render the gauge before a line is written.
Size ▰▱▱ minimum · ▰▰▱ medium · ▰▰▰ heavy  —  reach · depth · reversibility
Medium or heavy → offer a best-effort breakdown into minimum-sized steps.
↓

2. Acceptance

Name what done looks like — two or three observable outcomes, phrased as outcomes not actions, rendered alongside the gauge.
  • “the empty list renders the placeholder”, not “render the placeholder”
  • no observable surface (pure refactor, docs) → none — internal change
  • this is the target every later gate measures against
↓

3. Change Approval — gate

  • Free-form work → render the four-field block below, then await the user’s word.
  • Slash-invoked skill → the invocation is the word; run it. Skills carrying their own confirm step keep it; no outer gate is added.
  • Read-only turns are exempt, and a session-level opt-out (“just do it”) disables the gate for the session. Plan mode makes no difference either way. 
Size ▰▱▱|▰▰▱|▰▰▰ <minimum|medium|heavy> — <one-line why>
Acceptance:
- <observable outcome> (or: none — internal change)
Non-goals: <what this turn will deliberately not touch> (or: none)
Changes: <files and intent, one line>
Non-goals is a field, not a flourish: it is the line the Compliance Review reads as the one a diff must not cross. Write none when scope is unambiguous.
↓

4. Previews

Before the code, the picture — rendered into the standing /henneth window.
  • A UI change → a wireframe first, in both data states — populated and empty — one sketch per concern.
  • A UML concern (class, sequence, state, ER) → one diagram each; no data states.
  • Any generated plan → mirrored as plan-<topic>.html; the chat or markdown copy stays the source of truth.
The same session-level opt-out as the gate applies.
↓

5. Implementation Loop

Work the steps in order. Each step is closed by a named verification before the next begins.
  • Name the verification path before the step, so success and failure are recognizable. Where it cannot be automated — a wireframe to eye, a tone to feel — say so and describe the manual check standing in its place.
  • Steps are cut in layers, not slabs. The first builds the smallest thing that works end to end; each after it adds one capability atop something that already runs. Never trade a working product for unfinished complexity.
  • A step belonging to a /galadriel plan concept is ticked in place as it moves — - [ ] → - [~] before it begins, - [x] with its <!-- sha: … --> once verification closes it.
  • Step grew heavier than its gauge? Stop, re-gauge, re-summarize, await word.
  • Heavy tasks: a per-step Compliance audit fires after each step clears.
  • Context nearing its end mid-task? Write the baton to a /handoff channel named for the repo before anything else.
set -o pipefail; flutter analyze 2>&1 | tail -6
Trimming a check’s output must not swallow its exit code: a shell reports only the last stage of a pipe, and tail succeeds whatever the analyzer found. An unpiped command needs nothing.
↺ Divergence returns to the code. When the result diverges from what the plan called for, return to the code — do not bend the verification to fit the slip.
↓

6. Compliance Review — gate, before “done”

Spawn a lighter read-only agent over the cumulative diff, two passes in order:
  • Spec compliance — built what the plan named, nothing more, nothing less.
  • Code quality — reads true against the style/tool guides and local convention.
Three checks ride along when the change earns them, and each is easily skipped:
  • a new or edited user-facing string → read the sibling string’s actual current value, not its key, and flag divergence in shape;
  • translated strings across locales for a feature, or for privacy/legal copy → one read-only reviewer per non-English locale, in parallel;
  • a UI component’s render → invoke /manwe against the spec, or against a sibling component’s real layout values when there is none.
Findings: fix before “done”, or name plainly as a knowing exception. Fixes happen before the fresh verification — and a fix is itself code, so one pass of the project’s lint rides the fresh run beside the step’s own check.
↓

7. Fresh Verification — the last gate

Run the verification once more in the current turn — prior runs do not count.
✓ Walk each Acceptance line. Name the evidence that meets it — a passing test, a rendered screen, a logged value. An acceptance line with no evidence beside it is not met, and the loop is not closed.
↓

8. Done — spoken loud

Report what was completed, what was deferred, what remains uncertain. “Done” is wrong if anything was skipped silently — and “tests pass” is wrong if any were skipped, marked pending, or stubbed out. 
Compliance Review: PASS
Compliance Review: FAIL
Compliance Review: SKIPPED (reason: <one line>)
Close on one of those three lines, literally — the pulse regex-matches the string rather than guessing at prose, so a summary that only describes a clean review scores as none at all. The third is for a change a second reviewer would have nothing to weigh; it always names why.

Where Acceptance bites: stage 2 names the mark; stage 6’s spec pass reads it as “what the plan named”; stage 7 ticks it off line by line with evidence. Without it, stages 6 & 7 fall back to a target assembled after the fact — the one most easily bent to fit the slip.

Slash-invoked skills that name their own acceptance (e.g. /council’s Erestor) have already paid stage 2; the section binds free-form work.
