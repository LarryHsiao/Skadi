# Universal Engineering Rules

> Unlike `general.md`, `oo.md`, `flutter.md`, and `react.md` — which are personal taste, gated in `/mithrandir` to your own repos — rules here hold regardless of whose codebase the diff lives in. They travel onto every review, the way the official Effective Dart conventions in `dart-official.md` do, because the cost they guard against lands on whoever reads the code next, not on whoever holds the repo.
>
> Add new rules here, not as one-off exceptions threaded into a skill's prose — the container is the point.

## Duplication

- **Lift duplicate shapes on the third recurrence.** Two parallel uses of a small algorithm — a condition, a method body, a transform — may read true as honest repetition; a third is the threshold where the next reader pays a tax: touch one site and the question becomes *"did the other two move with it?"* Lift it then: a private helper, a shared utility, a base method named for the intent. The exception is structural look-alikes that bear *different* meanings — same five lines, different domain concern. Coupling those by name binds two things that should drift independently. Read each site's *why*, not its syntax; lift when the why matches, leave the shapes apart when it does not.
- **Count live call sites only.** A census taken before dead code is cleared counts sites that no longer execute — an orphaned copy inflates two honest recurrences into the three that the rule above keys on, arguing for an abstraction the live code alone would not warrant, and the false justification can reach a doc comment before a reviewer catches it. Clear the dead path first; count what still runs.

## Dependencies

- **Prefer an established library over a hand-rolled one — and surface the addition.** Common functionality — date arithmetic, argument parsing, retry with backoff — is a solved problem, and a hand-rolled copy carries the bugs the library has already fixed. Reach for a well-maintained one when it lowers overall complexity or raises reliability; judge it by total complexity carried, not by lines written. But a new dependency is not a free choice: it bears supply-chain, licence, and maintenance cost that the repo's owners carry long after the change lands. Name the package and the reason for it in the change summary and let the humans weigh it — never add one silently. Where the tree already carries a dependency that answers the need, that one wins outright over both the new package and the hand-roll.
- **Check the dependency's docs and types before declaring the gap.** *"The library does not do this"* is the assumption that produces the duplicate — a helper hand-written beside an API that already offered it, passing its tests, and costing the next reader two places to keep in step. Read the package's documentation and its type signatures before writing the substitute; where the capability is genuinely absent, name what you read to establish that. This is `CLAUDE.md`'s *Read Before Write* carried across the project's edge — the same discipline, applied to code you did not write but are about to lean on.
- **Read the vendor's own documentation before reverse-engineering its behaviour.** Reconstructing a third party's data format, pricing, or protocol from observed samples is rigorous and still misdirected when the vendor documents the thing outright, or offers a supported interface that makes the reconstruction unnecessary. Spend the one query before the first sample is measured: what do the official docs say? Where they name an interface as internal or version-unstable, that warning is a design input, not a footnote — carry it into the failure-mode comparison below rather than filing it as "noted". This extends *Check the dependency's docs and types* from a library's API to any third-party contract the code leans on.

## Failure Modes

- **Rank options by what failure costs, not by how likely failure is.** *"Will this break?"* is an engineering question; *"when it breaks, what is lost and who notices?"* is an architectural one, and the two orderings routinely disagree. For each candidate name four things — what breaks, how far it reaches, how soon it is noticed, and what cannot be recovered. A vendor's "this may change between releases" answers only the first question; on its own it must not decide the design.
- **Prefer the failure that is loud and local.** A blank panel anyone can see beats a collector that silently drops data no one misses until it is needed. Where the quiet option is chosen regardless, say plainly what its silent failure would cost and what would detect it. This is `CLAUDE.md`'s *Fail Loud* moved one step earlier — from how a result is reported to how the thing is built.
- **A stated, accepted maintenance cost is cheaper than an unbounded silent loss.** "The format may change and we will follow it" is a debt on a schedule; "the collector was never running, so those hours are gone" is not a debt at all — it is a hole.

## Resource Lifecycle

- **When a resource is hidden and reused rather than destroyed, the bound only holds on the happy path.** A pool that caps at one instance per key looks safe until the reuse handshake can fail — a timeout, a lock, a heartbeat — and the failure path forgets the old instance while minting a replacement. Audit that path on its own terms, and weigh whether the trigger is load-sensitive: a timeout that fires more often under load abandons more instances, and each abandoned instance adds load — a ratchet, not a plain leak. A comment explaining why the resource is hidden instead of destroyed should also name what the failure path costs; a justified design and a safe one are not the same claim.
- **A fixed delay guarding a variable-cost operation is not a synchronization primitive.** A timeout or interval sized to today's measured cost breaks the moment that cost rises, and the mechanism meant to guard against runaway work becomes the thing that fails under it. Where completion is knowable, signal it directly — an event, a generation token, a callback — rather than racing a clock against work of unknown duration.
