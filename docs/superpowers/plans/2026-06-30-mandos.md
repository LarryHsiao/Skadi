# /mandos Skill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `/mandos`, a skill that weighs a finished branch against its ticket's goal (council plan + ticket text + parent acceptance criteria) and pronounces a faithfulness verdict.

**Architecture:** A markdown `SKILL.md` owns argument dispatch, spec harvesting, branch/ticket resolution, and rendering; a read-only weighing subagent (prompt in `mandos.md`) judges the diff against the harvested decree, blind to any build conversation. Tracker reads reuse the council fetch hooks, extended with a small parent-ticket follow; PR/MR reads and writes reuse Lindir/Mithrandir hooks. A loop-neutral `[DOOM]` token is registered in council's grammar so a posted verdict never reads as fresh counsel.

**Tech Stack:** Bash + `curl` + `jq` + Python for hooks (matching existing `council-*-fetch.sh`); markdown skill files; the Agent tool for the weighing subagent; `gh`/`glab` via existing hooks for forge I/O.

## Global Constraints

- Skill files are the source of truth in this repo; live copies under `~/.claude/` are written **only** by the `/install` skill — never hand-edit `~/.claude/`.
- Hook scripts live under `hooks/`, are `chmod +x`, and each must have a portable `Bash(~/.claude/hooks/<name>.sh:*)` entry in `settings.json` `permissions.allow` (no absolute paths).
- Tracker routing: reuse `tracker_routing.md` (MET→youtrack, PSG→jira). Do not hardcode project-key lists.
- **Jira is read-only for tests.** Never post test comments to Jira. Write-path smoke tests run against YouTrack **MET-1**.
- Credentials resolve through `hooks/secret.sh` (vault first, env fallback) — never read a token directly from an env var in a hook.
- Domain/OO and general style guides in `docs/style/` apply to any non-trivial logic.
- Token names: primary `[DOOM]`, alias `[VERDICT]`. Tier labels: `Faithful` / `Hold` / `Astray`. Gauge glyphs: `▰▱▱` / `▰▰▱` / `▰▰▰`.

### Task 1: Parent-ticket fetch — extend both council fetch hooks

**Files:**
- Modify: `hooks/council-jira-fetch.sh` (add `parent` field + parent follow)
- Modify: `hooks/council-youtrack-fetch.sh` (add `parent` field + parent follow)
- Test: manual smoke (no unit harness for shell hooks in this repo) — documented below

**Interfaces:**
- Produces: each fetch hook's JSON gains a top-level `parent` key:
  ```json
  { "summary": "...", "description": "...", "comments": [...],
    "parent": { "id": "EPIC-12", "summary": "...", "description": "..." } }
  ```
  `parent` is `null` when the ticket has no parent. The weighing step reads
  `parent.description` for an acceptance-criteria list.

- [ ] **Step 1: Add the parent field to the Jira issue fetch**

In `hooks/council-jira-fetch.sh`, change the issue fetch path to request `parent`:

```bash
if ! fetch_to_file "issue" "/rest/api/3/issue/$ISSUE_KEY?fields=summary,description,parent" "$issue_file"; then
  exit 1
fi
```

- [ ] **Step 2: Fetch the parent issue when present (Jira)**

After the comments fetch, before the Python block, read the parent key from the
issue file and fetch the parent's fields into a third temp file:

```bash
parent_file=$(mktemp)
trap 'rm -f "$issue_file" "$comments_file" "$parent_file"' EXIT
PARENT_KEY=$(jq -r '.fields.parent.key // empty' "$issue_file")
if [[ -n "$PARENT_KEY" ]]; then
  if ! fetch_to_file "parent" "/rest/api/3/issue/$PARENT_KEY?fields=summary,description" "$parent_file"; then
    exit 1
  fi
fi
```

- [ ] **Step 3: Emit the parent block in the Jira Python output**

Extend the Python `out` dict (pass `parent_file` as `sys.argv[3]`, may be empty):

```python
parent_path = sys.argv[3] if len(sys.argv) > 3 else ""
parent = None
if parent_path:
    try:
        pj = json.load(open(parent_path, "r", encoding="utf-8"))
        pf = pj.get("fields") or {}
        if pj.get("key"):
            parent = {"id": pj["key"],
                      "summary": pf.get("summary") or "",
                      "description": adf_to_text(pf.get("description"))}
    except Exception:
        parent = None
out["parent"] = parent
```

Update the heredoc invocation to pass the third arg:

```bash
PYTHONPATH="$(dirname "$0")" python - "$issue_file" "$comments_file" "$parent_file" <<'PY'
```

(When no parent, `$parent_file` is an empty temp file; the `try` yields `parent=None`.)

- [ ] **Step 4: Add the parent field + follow to the YouTrack fetch**

In `hooks/council-youtrack-fetch.sh`, request the parent link in the issue fetch.
YouTrack exposes the parent via the `Subtask` link's `issues` array:

```bash
if ! fetch_to_file "issue" "/api/issues/$TICKET_ID?fields=summary,description,parent(issues(idReadable,summary,description))" "$issue_file"; then
  exit 1
fi
```

- [ ] **Step 5: Emit the parent block in the YouTrack jq output**

Extend the `jq -n` filter to project the parent (first linked parent issue, if any):

```jq
parent: (($issue.parent // {}) | .issues // [] | (if length > 0 then
  { id: (.[0].idReadable // ""), summary: (.[0].summary // ""), description: (.[0].description // "") }
  else null end))
```

- [ ] **Step 6: Smoke-test both hooks against real tickets**

Run (YouTrack — a real MET ticket; read-only, safe):

```bash
~/.claude/hooks/council-youtrack-fetch.sh MET-1 | jq '{has_parent: (.parent != null), parent_id: .parent.id}'
```

Expected: valid JSON, `has_parent` true or false (no error). For Jira, run the
same shape against a real PSG key **read-only**:

```bash
~/.claude/hooks/council-jira-fetch.sh PSG-1 | jq '.parent'
```

Expected: a parent object or `null`, never a stack trace. If YouTrack's
`parent(...)` field path errors (older instance), adjust to the
`/api/issues/$TICKET_ID/links?fields=direction,linkType(name),issues(idReadable,summary,description)`
form and filter `linkType.name == "Subtask"` with `direction == "INWARD"`.

- [ ] **Step 7: Commit**

```bash
git add hooks/council-jira-fetch.sh hooks/council-youtrack-fetch.sh
git commit -m "feat(mandos): council fetch hooks follow parent ticket for AC"
```

### Task 3: SKILL.md skeleton — frontmatter and argument dispatch

**Files:**
- Create: `skills/mandos/SKILL.md`

**Interfaces:**
- Produces: a `user_invocable` skill whose dispatch resolves one of five paths
  from the first positional — branch (none), ticket-id, URL, `post`, `comment` —
  plus the `--deep`, `--plain`, `--lore` flags. No weighing logic yet.

- [ ] **Step 1: Write the frontmatter and the dispatch section**

Create `skills/mandos/SKILL.md` with YAML frontmatter (`name: mandos`,
`user_invocable: true`, and a `description` covering the five forms and three
flags, in the style of `skills/mithrandir/SKILL.md` line 3). Add an "Argument
parsing" section enumerating:

```
/mandos                      # branch-primary
/mandos TICKET-ID            # ticket-primary
/mandos <pr-or-mr-url>       # URL form
/mandos post TICKET-ID       # write → ticket [DOOM] post (confirm-once)
/mandos comment <url>        # write → PR/MR comment (confirm-once)
--deep | --plain | --lore    # flags
```

Dispatch on the first positional: empty → branch-path; `post` → ticket-write;
`comment` → forge-write; `http(s)://` prefix → URL-path; otherwise treat the
token as a TICKET-ID → ticket-path. `--plain`/`--lore` mutually exclusive (stop
if both); `--deep` composes with any path.

- [ ] **Step 2: Write the Ethos and Tracker-routing sections**

Mirror `skills/council/SKILL.md` "Tracker routing" (hybrid dispatch: explicit
prefix → `tracker_routing.md` → ask-and-save) and add an Ethos block: judges

independent of chat; advisory, never auto-gates a merge.

### Task 4: Spec harvest + branch/ticket resolution

**Files:**
- Modify: `skills/mandos/SKILL.md` (add "Spec harvest" and "Resolution" sections)

**Interfaces:**
- Consumes: the council fetch hooks' JSON (now bearing `parent`), the
  `[GWAITH]` forge comment, and git branch/commit metadata.
- Produces: an in-memory **decree** — a folded list of acceptance items drawn
  from `[COUNSEL]`/`[PLAN]`, ticket text, and `parent.description` — plus the
  resolved `(branch, base, ticket-id)` triple and the captured diff.

- [ ] **Step 1: Write the "Spec harvest" section**

Document the three-source fold:
1. Fetch the ticket via the routed fetch hook; take its newest `[COUNSEL vN]` /
   `[PLAN]` comment body as the detailed plan.
2. Take `summary` + `description` as the ticket text; scan for an AC list
   (lines under a heading matching `acceptance`/`AC`/`criteria`, or a checkbox
   list).
3. If `parent` is non-null, scan `parent.description` for an AC list the same way.
Fold all found acceptance items into one ordered list, tagged by source
(`[COUNSEL]`, `<ticket-id>`, `<parent-id> AC`).
**No-AC fallback:** if no explicit AC anywhere, derive implicit acceptance from
the description and **state plainly in the render that the gate is softer.**

- [ ] **Step 2: Write the "Resolution" section (both directions)**

- **Branch-path:** resolve base via the `master`/`main`/`origin/HEAD` ladder
  (copy the exact `git rev-parse` ladder from `skills/mithrandir/SKILL.md`
  step 1). Refuse to run on the base branch. Derive ticket-id from the branch
  name prefix (`^[A-Z]+-[0-9]+`) or, failing that, the first such token in
  `git log <base>..HEAD --format=%s`.
- **Ticket-path:** fetch the ticket; find the `[GWAITH]` comment and read its
  branch + PR/MR URL; if absent, fall back to a local branch whose name carries
  the ticket-id prefix. Capture the diff via
  `git diff $(git merge-base HEAD <base>)..HEAD` against that branch.
- **URL-path:** invoke the Lindir read hook (`lindir-github-pr.sh` /
  `lindir-gitlab-mr.sh`) for metadata + `--diff`; read the ticket-id from the
  PR/MR title or source-branch name, then harvest its decree.

- [ ] **Step 3: Verify resolution against a real ticket (read-only)**

On a branch named like `MET-1-foo`, run `/mandos` and confirm it reports the
derived ticket `MET-1`, the resolved base, and a non-empty decree (or the
softer-gate notice). On `/mandos MET-1`, confirm it resolves a branch (or says
plainly none was found). No verdict yet — this checks harvest + resolution only.

- [ ] **Step 4: Commit**

```bash
git add skills/mandos/SKILL.md
git commit -m "feat(mandos): spec harvest (plan+ticket+parent AC) and resolution"
```

### Task 5: The weighing subagent + render

**Files:**
- Create: `skills/mandos/mandos.md` (read-only weigher prompt)
- Modify: `skills/mandos/SKILL.md` (add "Weigh" and "Render" sections)

**Interfaces:**
- Consumes: the decree (Task 4) and the captured diff.
- Produces: three buckets — **Covered** (with `file:line`), **Missing** and
  **Scope-crept** (each severity-tagged Blocker/Nice-to-have/Nit) — and an
  overall tier (`Faithful`/`Hold`/`Astray`) by the gate rule.

- [ ] **Step 1: Write the weigher prompt `mandos.md`**

The prompt charges a read-only `general-purpose` agent (model: opus) given ONLY
the decree and the diff (never the build conversation) to: walk each acceptance
item, mark it Covered (cite `file:line`) or Missing (severity); then in one pass
name any diff change no item asked for as Scope-crept (severity). Return a
structured body: the three buckets and a one-line per-item verdict. Read-only —
no edits, commits, or posts.

- [ ] **Step 2: Write the default "Weigh" section in SKILL.md**

Default (holistic): dispatch one weigher subagent with the whole decree + diff.
`--deep`: partition the decree into individual items; dispatch one weigher per
item (cap concurrency, queue rest), each handed only its one item + the full
diff; aggregate verdicts; judge Scope-crept in one final leftover-diff pass.
State the `--deep` tail-line: *"Deep mode — N criteria weighed each on its own."*

- [ ] **Step 3: Write the "Render" section + gate rule**

Document the render block (Covered / Missing / Scope-crept sections, omit-empty
subsections, blockquote header, `## Doom <gauge> <tier>` + one closing
paragraph), exactly as the spec's render sketch. Gate rule: any Blocker → Hold
(several Blockers → Astray); only Nits → Faithful; clean → Faithful. Tone:
lore in chat by default, plain on forge/ticket; `--plain`/`--lore` override.

- [ ] **Step 4: Smoke-test a full read-path verdict**

On a real feature branch with a known ticket, run `/mandos`. Expected: a
rendered verdict with at least the Covered bucket populated, an overall tier,
and a closing paragraph — grounded with `file:line` citations. Run `/mandos
--deep` on the same branch; expect the per-criterion tail-line and the same
bucket structure.

- [ ] **Step 5: Commit**

```bash
git add skills/mandos/mandos.md skills/mandos/SKILL.md
git commit -m "feat(mandos): read-only weigher subagent, deep mode, and render"
```

`comment <url>`: render the verdict in **plain** tone (no `[DOOM]` token — the
forge isn't parsed by council); confirm-once; on Yes, post via the routed
Mithrandir comment hook (`mithrandir-github-comment.sh` /
`mithrandir-gitlab-comment.sh`); surface the hook's success/error line verbatim;
never retry.
